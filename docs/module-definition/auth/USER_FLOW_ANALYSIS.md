# 認証フロー ユーザー操作分析

> 作成日: 2026-02-21
> 対象: `docs/agent-tasks/architecting/0004_design_and_auth.md` および
>       アプリへの Google Drive 連携組み込み計画（feature/google-auth）

---

## 目的

実装計画に基づいたとき、**ユーザーがどのフェーズで認証を求められるか**を分析する。
この結果を踏まえ、実装方針の最終判断を行う。

---

## 認証が発生するポイント（現計画ベース）

現計画では、認証は以下の **3 つの局面** で発生する。

| # | 局面 | 表示される UI | ユーザー操作 | 発生頻度 |
|---|------|-------------|------------|---------|
| 1 | **アプリ起動時**（毎回） | ローディング画面（"読み込み中..."） | なし（自動） | 毎回 |
| 2 | **未ログイン状態でのアクセス時** | LoginPage（"Googleでログイン"） | ボタンクリック + OAuth同意 | 初回 / ログアウト後 |
| 3 | **初回ログイン後（スプレッドシート未設定）** | SpreadsheetSetupModal | 「作成」または「ID入力」 | 初回のみ |

---

## シナリオ別ユーザーフロー

### シナリオ A: 初回ユーザー

```
アプリを開く
  ↓
[ローディング画面] ★局面1
  → initializeDatabase() 呼び出し
  → Google API スクリプト読み込み待機（async）
  → localStorage にトークンなし → GuestState
  ↓
[LoginPage 表示] ★局面2
  "Googleでログイン" ボタン
  ↓
[Google OAuth 同意画面（外部）]
  ↓
[SpreadsheetSetupModal 表示] ★局面3
  "新しいスプレッドシートを作成"
  → Google Drive にシート作成
  → localStorage に ID 保存
  ↓
[Dashboard 表示] ← アプリ正常使用開始

総ステップ数: ローディング → ログイン → OAuth → スプシ設定 → アプリ（4ステップ）
```

---

### シナリオ B: リターンユーザー（有効トークンあり）

```
アプリを開く
  ↓
[ローディング画面] ★局面1
  → initializeDatabase() 呼び出し
  → localStorage のトークンを取得
  → gapi.client でトークンをセット
  → fetchUserInfo() でトークン有効性をネットワーク検証
  → isSignedIn: true をブロードキャスト
  ↓
[Dashboard 表示] ← 認証は完全に透明（ユーザー操作なし）

総ステップ数: ローディング → アプリ（1ステップ）
```

**重要**: ネットワーク検証（`fetchUserInfo`）が含まれるため、
ローディング画面は毎回表示される。オフライン環境での動作は未定義。

---

### シナリオ C: トークン期限切れ（1時間経過後に再起動）

```
アプリを開く
  ↓
[ローディング画面] ★局面1
  → localStorage のトークンを取得
  → expiresAt を確認 → 期限切れ → clearToken()
  → GuestState
  ↓
[LoginPage 表示] ★局面2
  → ログイン操作（シナリオ A の局面2 と同じ）
  ↓
[Dashboard 表示（SpreadsheetSetupModal は表示されない）]
  ← localStorage に BODYANALYST_SPREADSHEET_ID が残っているため

総ステップ数: ローディング → ログイン → OAuth → アプリ（3ステップ）
```

---

### シナリオ D: 手動ログアウト後

```
設定画面で「ログアウト」をタップ
  ↓
[signOut() 実行]
  → サーバー側トークン無効化
  → gapi.client.setToken(null)
  → localStorage から google_auth_token 削除
  → isSignedIn: false をブロードキャスト
  ↓
[AuthGuard] が検知 → /login へリダイレクト
  ↓
[LoginPage 表示] ← 即時（ローディングなし）

ログアウト → ログイン:
  シナリオ C の「トークン期限切れ後再起動」と同じフロー
```

---

### シナリオ E: ⚠️ セッション中のトークン失効（未対処）

```
アプリを使用中（ログイン済み状態）
  ↓
[経過時間: 約1時間（Google OAuth トークンの有効期限）]
  ↓
[ユーザーがデータ保存などの操作を実行]
  ↓
[Google Sheets API 呼び出し → 401 Unauthorized]
  ↓
[リポジトリがエラーをスロー]
  ↓
[UI にエラー表示（想定）] ← 再認証への誘導なし

現象:
  - isSignedIn: true のまま（gapi.client はトークンを持ち続ける）
  - AuthGuard はログイン済みと判断するため /login へ飛ばない
  - ユーザーは「ログインしているのにデータが保存されない」状態に陥る
```

---

## 問題点の整理

### P1（本番ブロッカー）

| 問題 | 説明 | 影響 |
|------|------|------|
| **セッション中トークン失効の未対処** | 1時間後にAPIコールが全失敗する。AuthGuardは再認証を促さない | データの読み書きが無音で失敗。ユーザーは原因が分からない |

### P2（UX 問題）

| 問題 | 説明 | 影響 |
|------|------|------|
| **毎回ローディング画面が表示される** | `initializeDatabase()` が常にネットワーク検証（`fetchUserInfo`）を行う | リターンユーザーの起動体験が悪い。特にモバイル・低速回線で顕著 |
| **SpreadsheetSetupModal の閉鎖不可** | 閉じるボタンがない設計 | 誤って ID を入力した場合の訂正手段がない。アカウントの切り替えができない |
| **初回フローが4ステップ** | ローディング→Login→OAuth→スプシ設定 | オンボーディングの離脱リスク |

### P3（設計上の考慮点）

| 問題 | 説明 |
|------|------|
| **スプレッドシート ID が localStorage のみ** | デバイス切り替え時に再設定が必要 |
| **ルーティング仕様との乖離** | `docs/system_architecture/routing/SPECIFICATIONS.md` ではすべてのルートが "Public" と定義されている。AuthGuard の追加はこの仕様の変更を意味する |
| **BrowserRouter の遅延マウント** | `AppInitStatus === 'ready'` になるまで Router がマウントされない。ブックマークした URL（例: `/workout`）が、初期化完了まで処理されない |

---

## 対処オプション（P1・P2 のみ）

### P1: セッション中トークン失効への対処

**Option A: サイレントトークン更新（推奨）**
- GIS の `requestAccessToken()` を `prompt: ''` で呼ぶと、ユーザー操作なしで新トークンを取得できる
- リポジトリが 401 を受け取ったタイミングで自動的にリフレッシュしてリトライ
- `BaseRepository` に `onAuthError` ハンドラを追加

**Option B: 定期チェック**
- `setInterval` で `isTokenValid()` を確認し、期限切れ前にトークンを更新
- 実装はシンプルだが、バックグラウンドで不要なネットワーク呼び出しが発生する

**Option C: スコープ外（MVP では許容）**
- エラーメッセージに「再読み込みしてください」を表示し、ユーザーに手動対処を求める
- MVP として許容可能な場合は最初の計画通りで進め、後続スプリントで対処

### P2: 毎回ローディング画面への対処

**Option A: localStorage のトークンチェックを先行表示（推奨）**
- `localStorage` に有効なトークンが存在すれば、ネットワーク検証前にアプリをレンダリングして始める
- バックグラウンドで `fetchUserInfo()` を実行し、失敗時のみ `/login` へリダイレクト
- ローディング画面は「初回 / トークンなし」の場合のみ表示される

**Option B: 現行計画を維持（スコープ内）**
- ローディング画面は受け入れる。将来的にスケルトン UI に置き換える
- MVP として許容可能

---

## 結論と推奨判断

| 項目 | 推奨 | 理由 |
|------|------|------|
| **P1（トークン失効）** | **Option C（スコープ外/MVP許容）** で実装開始し、後続対処 | まず動くものを作ることが優先。Google OAuth の implicit grant は1時間有効で、通常のトレーニング記録セッションには十分 |
| **P2（ローディング）** | **現行計画を維持（Option B）** | MVP フェーズでは許容範囲。スケルトン UI への改善は別タスクとして切り出す |
| **SpreadsheetSetupModal** | **キャンセルボタンを追加し、ログアウトに誘導する** | 完全閉鎖不可は UX 上のリスク。「キャンセル（ログアウト）」で GuestState に戻れるようにすべき |
| **ルーティング仕様** | **`docs/system_architecture/routing/SPECIFICATIONS.md` を同時に更新** | AuthGuard の追加は仕様変更。ドキュメントの整合性を保つ |

---

## 補足: 認証が**発生しない**ユーザー操作

以下の操作中は、認証画面は表示されない（設計通り）:

- BottomNav によるページ間のナビゲーション
- ダッシュボードのチャート操作
- ワークアウト記録・食事記録・体重記録の入力
- 設定画面でのカラーテーマ変更

認証は「起動時」と「未認証アクセス時」にのみ発生する境界設計となっている。
